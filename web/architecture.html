THE SYSTEM BEHIND THE ANSWER

Gemini interprets. The platform validates.

Two bounded Gemini calls connect a shopping request to eligible catalog evidence. The service checks the model’s outputs, and the shopper approves a separate request before any draft is created.

Open full-size diagram ↗ Read the technical design ↗
01 · UNDERSTAND

Request → tool call

The independent parser checks supported requests. Gemini returns one search_catalog call. The server requires its normalized constraints to match the parser before searching.

02 · GROUND

Catalog → verified offer

The service filters permissions, freshness, stock and customer constraints. A second Gemini call selects an offer ID from eligible evidence; the server verifies it against the lowest eligible price.

03 · ACT

Approval → one draft

The shopper clicks Prepare demo cart. For a new draft, the service revalidates the proposal and current records. A Firestore transaction creates one draft. A retry with the same key returns the existing draft before those checks.

Gemini is selected by default and requires local server credentials. No model call runs merely by opening this page or the app. Offline Demo is an explicit option that skips both model calls. Catalog data is synthetic, the trace arrives with the completed response, and draft creation does not purchase, pay, reserve stock or contact a merchant.
